# 点赞只为已有问答缓存续期，关闭 hotqa 永久缓存层

grid-qa 的 hotqa 把用户点赞过的问答对写入 Redis（`hotqa:{问题}`，永不过期），放在问答链路最前面，命中后跳过检索、纠错与生成，并一律返回"高置信"。它绕过了普通问答缓存的全部保护：不区分租户、纠错模式与模型；命中前不复核证据文档（撤回、过期、租户归属）；文档删除或更新时不失效；单次点踩不失效；来源只剩文档名，引用无法核对。一个用户点一次赞就能让答案对所有人永久生效——实际发生过：一条结构化拒答被点赞后，以"高置信"永久返回。

改为把三件事交给各自合适的信号：**是否缓存**由系统分级决定（只有 high 置信写入普通缓存，原有行为）；**缓存多久**由用户反馈调节（点赞把已有条目的有效期延长到 7 天，`LIKE_CACHE_TTL`）；**命中时是否仍有效**由知识状态决定（原有的租户隔离、证据时效复核、文档变更与点踩失效）。

## Consequences

- `HOTQA_ENABLE` 默认改为 false，读取代码保留在开关之后；点赞不再写 hotqa，改调 `feedback_optimizer_service.extend_cache_on_like`。
- 点赞只续期、不新增条目：拒答与证据有限（medium）的回答本就不进缓存，点赞后也不会被复用。如实回答不需要点赞即可被缓存（3 天）。
- 续期的键与问答页一致（默认模型 + 默认纠错模式 + 租户 + 归一化问题），Redis 与 MySQL 两层同时延长，只延长不缩短。
- 有效期仍有上限：缓存键不含提示词、检索参数与图谱版本，这类变更后旧答案不会被主动清除，7 天上限是兜底。
- 显式指定 `correctionMode` 的请求（对照页、评测）本来就跳过 hotqa；评测请求带 `noCache`，不读写任何缓存，评测结果不受影响。

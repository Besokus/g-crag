# G-CRAG 系统设计文档

> 版本 v2.0（2026-09-26），取代 v1.0 的"从零自建"设计。
> 术语以根目录 `CONTEXT.md` 为准；决策依据见 `docs/adr/`。
> 文中 `file:line` 均指原版 grid-qa 仓库中的位置。

---

## 1. 设计目标

| 目标 | 设计手段 |
|---|---|
| 图谱真正参与纠错 | 图谱定位证据作为首选纠错动作（§6、§8） |
| 分级信号可信 | 修复 rerank 失败被误判的缺陷；打分器接口；录制回放（§5） |
| 核心通用、领域可配 | 核心链路 + 数据型领域包 + 扩展点（§3） |
| 结果可对照 | 三种纠错模式共用同一链路，只切换纠错逻辑（§6.3） |
| 过程可观测 | 纠错每一步写入轨迹，含证据路径（§10） |
| 纠错有界 | 最多两轮纠错；用尽后拒答（§6） |

## 3. 领域包（ADR 0002、0005）

### 3.1 原则
- 领域包**只含数据**，不含代码。
- 核心链路在需要领域知识处定义**扩展点**，并实现若干通用策略；领域包只**选择策略、配置参数、提供数据**。
- 部署级生效：后端启动时按 `DOMAIN_PACK` 加载唯一领域包，用 pydantic 校验，失败即启动报错。

### 3.2 目录格式
```
domain_packs/<name>/
├── pack.yaml         # 元数据 + 各扩展点的策略选择与参数
├── schema.yaml       # 实体类型、关系白名单
├── aliases.json      # 别名 → 标准实体名
├── normalize.yaml    # 归一化规则（映射 + 正则）
├── prompts/          # 抽取、角色、拒答等措辞片段（模板变量）
├── seed/             # 种子语料
└── eval/             # 评测集
```

```yaml
# pack.yaml
name: general
display_name: 通用
entity_linking:
  chain: [dictionary, embedding]
  embedding_threshold: 0.75        # 需标定
graph_evidence:
  max_hops: 2
  hub_degree: 30                   # 度数超过即为枢纽实体
  start_hub_max_hops: 1            # 起点本身是枢纽实体时只扩展 1 跳
  max_candidates: 30
scorer:
  name: dashscope_rerank
  high: null                       # null = 使用该打分器的标定值
  low: null
chunking:
  size: 500
  overlap: 50
doc_type_rules: []                 # 文件名 → 文档类型
```

### 3.3 扩展点清单
| 扩展点 | 领域包提供 | 原硬编码位置 | 核心改造 |
|---|---|---|---|
| 实体类型 / 关系白名单 | `schema.yaml` | `kg_service.py:29` prompt 文本 | prompt 模板化，由 schema 渲染 |
| 抽取措辞 | `prompts/extract.md` | `kg_service.py` `_KG_PROMPT_V2` | 同上 |
| 实体归一化 | `normalize.yaml` | `kg_normalize.py` | 规则引擎化，读配置 |
| 术语/别名 | `aliases.json` | `term_service` 读 `data/grid_terms.json` | 改读领域包 |
| 分词词典 | `aliases.json` + 实体名 | jieba 默认词典 | 启动时加载为自定义词典 |
| 查询分类规则 | `pack.yaml` | `routing/query_classifier.py` | 规则外置 |
| 安全规则 | `pack.yaml` | `core/safety.py` | 通用部分留核心，领域部分外置 |
| 角色/拒答措辞 | `prompts/` | `qa_service`、`multimodal_service` 各 prompt | 模板化 |
| 文档类型推断 | `doc_type_rules` | `kb_seed/seed_kb.py` 文件名前缀 | 规则外置 |
| 实体链接 / 图谱定位证据 / 打分器阈值 | `pack.yaml` | 新建 | 新建 |

### 3.4 命名空间隔离（ADR 0005）
| 存储 | 隔离方式 |
|---|---|
| MySQL | 每个领域包一个 database（`gcrag_<pack>`），启动时由 `init_db` 建表与补列（见 §16.7） |
| Milvus | collection 名 `<pack>_chunks` |
| Neo4j | 所有节点与关系带 `pack` 属性，所有查询带 `pack` 条件（Community 版只有一个库） |
| Redis | key 前缀 `<pack>:` |
| MinIO | 对象前缀 `<pack>/` |

> **本期做法（截止前）**：每个领域包单独起一个 docker compose project（`-p gcrag-<pack>`），数据卷天然隔离，上表的字段级隔离推迟（开发方案 §4.2）。因此本期 §4、§8、§16 中的存储结构都**不带 `pack` 字段**。

### 3.5 两个领域包
- **电网领域包 `grid`**：由 grid-qa 原有 schema、归一化规则、`grid_terms.json`、prompt 措辞、`kb_seed/` 抽取而成；只用于演示与复盘。
- **通用领域包 `general`**：通用实体类型（人物、组织、地点、事件、时间、作品、产品、概念等）+ 通用关系白名单，别名表为空；语料为 CRUD-RAG 新闻；主评测使用。

## 4. 建图与出处 chunk（ADR 0004）

### 4.1 抽取流程
```
文档所有 chunk（按 chunk_idx）
 → 每 6 个一批，编号 [1]…[6] 拼接
 → LLM 按 schema 抽取，每条三元组输出 {s, r, o, chunk_no}
 → 归一化（领域包规则）+ 白名单过滤 + 去重
 → 出处校验（§4.2）
 → 写 MySQL KgTriple + Neo4j（MERGE，带 pack、chunk_id）
 → 计算实体度数写入节点属性 degree
 → 实体名向量化（云端 embedding）写入实体向量表
```

### 4.2 出处校验
```
候选 chunk = 批内第 chunk_no 个
若 s 与 o（或其别名）都出现在候选 chunk → 采用
否则 在同批 6 个 chunk 中找同时包含 s 与 o（或别名）的 chunk
       找到唯一或第一个 → 采用
       找不到 → chunk_id 置空（只保留文档级关联，不参与图谱定位证据）
```
- 匹配时既比对归一化后的名称，也比对归一化前的原文写法（抽取时一并保留原文写法 `s_raw`、`o_raw`）。
- 统计并记录"校验通过 / 同批重找 / 置空"三类比例，作为报告数据。

### 4.3 数据模型变更
详见 §16.7。要点：
- MySQL `KgTriple` 新增 `chunk_id`、`s_raw`、`o_raw`、`provenance`，一行对应一次"三元组 + 出处 chunk"。
- Neo4j 的关系仍按 (主语, 类型, 宾语) 合并为一条边，但出处用**列表** `chunk_ids` / `doc_ids` 累积——同一关系可能来自多个 chunk，原实现只保留首个 `doc_id`。
- `:Entity` 新增 `degree`；实体向量存 MySQL 表 `entity_embedding`。

### 4.4 重建
`extract_triples` 原为增量追加（不清旧）。新增重建脚本：按领域包清空 KgTriple、Neo4j 中 `pack` 相同的节点和关系、实体向量表，再对全部文档重新抽取；支持断点续跑（按文档记录完成状态）。

## 5. 检索分级与打分器（ADR 0006）

### 5.1 原有纠错的分级信号缺陷
| 位置 | 问题 |
|---|---|
| `retrieval_service.py:449-460` | rerank 超时（2s）或失败时，`_rr_ok` 只写入轨迹，不返回；结果保留 RRF 分数 |
| `qa_service.py:226` | 分级用 `rerank_ok = settings.RERANK_ENABLE`（配置开关），恒为 True |
| `rag/rrf.py:19` | 混合检索 RRF 分数约 0.016~0.03，远低于 `CRAG_LOW=0.3` → **全部判 incorrect → 改写 → 拒答** |
| `retrieval_service.py:138-151`、`:372-375` | 单路 BM25 分数归一到 top1=1.0；高置信 sparse 路由跳过 rerank → **全部判 correct，纠错永不触发** |
| `rerank_service.py:44` | 无 `DASHSCOPE_API_KEY` 时返回全 0 分 → 全部拒答 |

> 现有阈值：`CRAG_HIGH=0.72`、`CRAG_LOW=0.3`（`config.py:181-188`），运行时可被 Redis `config:crag` 覆盖（`config_service.rt_crag_high/low`）。

### 5.2 修复
1. 检索结果返回结构新增 `scoring = {scorer, ok, reason}`，由检索服务如实填写本次打分是否成功。
2. 分级只读取 `scoring.ok`，不再读配置开关。
3. 纠错模式为原有纠错或 G-CRAG 时，**不跳过 rerank**（分级依赖打分器分数）。
4. `scoring.ok = False` 时不分级：不纠错，置信度标为"不确定"，轨迹记录降级原因。

### 5.3 打分器接口
```python
class Scorer(Protocol):
    name: str
    async def score(self, query: str, texts: list[str]) -> ScoreResult: ...
    # ScoreResult = {ok: bool, scores: list[float], reason: str}
```
- 当前唯一实现：`DashscopeRerankScorer`（gte-rerank-v2）。
- 阈值与打分器绑定：`scorer_thresholds/<scorer>.yaml` 保存标定值，领域包可覆盖。

### 5.4 录制回放
- 键：`sha256(scorer_name | query | text)`，值：分数。
- 模式：`SCORER_CACHE=off | record | replay`。评测首跑用 `record`，重跑用 `replay`；`replay` 未命中时实时调用并补录。
- 存储：本地 JSONL 文件，随评测结果一起归档。

## 6. G-CRAG 纠错流程

### 6.1 状态流转
```
检索 → 检索分级
 ├─ 打分失败 → 不纠错，标"不确定" → 生成
 ├─ correct → 生成
 ├─ ambiguous → [第1轮] 图谱定位证据 → 合并上下文 → 统一 rerank → 再分级
 │               ├─ correct / ambiguous → 生成（ambiguous 标不确定）
 │               └─ incorrect → 进入下方 incorrect 的第 2 步
 └─ incorrect → [第1轮] 图谱定位证据 → 合并 → rerank → 再分级
                 ├─ correct / ambiguous → 生成
                 └─ incorrect → [第2轮] 原有纠错（LLM 改写重检索）→ 再分级
                                 ├─ 非 incorrect → 生成
                                 └─ incorrect → 拒答 → 证据补全队列
```
- 图谱定位证据前若实体链接无结果，跳过该动作，直接进入下一步，轨迹记录"未链接到实体"。
- 最多两轮纠错。
- 实现（M6c，`rag/gcrag.py`）补充的三条规则：
  1. **三种模式都强制打分**（`force_score=True`），不只 legacy/gcrag。否则 none 模式在高置信 sparse 路由下跳过 rerank，上下文排序与另两种模式不同，违背"模式之间唯一的差别是纠错"。
  2. **合并后分级不会变差**：合并只增加候选；若重打分后分级反而下降（重打分用原问题，初次检索内部用改写后的查询，分数有出入），本轮记为 `no_improvement`，保持原上下文与原分级。
  3. **任何一轮的检索打分失败都记为 `unscored`**，不据此拒答（与 §5.2 一致）。

### 6.2 挽回的判定
某轮纠错后分级由 ambiguous/incorrect 变为可作答，记为该动作"触发挽回"；评测时再结合答案判定得到挽回率（见 §11.4）。

### 6.3 纠错模式开关
`CORRECTION_MODE = none | legacy | gcrag | gcrag_v2`

| 模式 | ambiguous | incorrect |
|---|---|---|
| none | 生成 | 生成 |
| legacy | 生成（标不确定） | LLM 改写重检索 → 仍 incorrect 拒答 |
| gcrag | 图谱定位证据 | 图谱定位证据 → LLM 改写 → 拒答 |
| gcrag_v2 | 同 gcrag | 同 gcrag |

对照页与评测脚本可按请求覆盖该开关（`/qa/answer` 增加可选参数 `correctionMode`）。

**gcrag_v2（2026-10-01，test2 之后的事后迭代，需在报告中如实标注）**：分级与采纳判定和 gcrag 完全相同，只改采纳后的上下文——gcrag 取"原上下文 ∪ 图谱候选"重打分后的 topk，图谱条目可能挤掉有用的检索条目（test2 t30）；gcrag_v2 原检索条目原样保留（顺序、分数不变），只把进入重打分 topk 的图谱条目追加在后面，上下文最多 2×topk 条。

### 6.4 代码落点
- 新建 `rag/gcrag.py`：纠错编排（状态流转、轮次上限、轨迹事件）。
- `qa_service` 中原 CRAG 分支（`:210-300`）改为调用 `gcrag.correct(...)`，legacy 模式在其中复用原逻辑。
- 删除原 ambiguous 相邻 chunk 扩展（`CRAG_NEIGHBOR_EXPAND_ENABLE`），由图谱定位证据取代。

## 7. 实体链接

### 7.1 策略链
按 `pack.yaml` 中 `entity_linking.chain` 顺序执行，前一个策略命中即停止。

| 策略 | 做法 | 特点 |
|---|---|---|
| `dictionary` | 词典 = 图谱全部实体名 + 领域包别名；在问题文本上做最长匹配（Aho-Corasick 或 jieba 自定义词典） | 零 LLM 成本、结果确定；换说法时漏召回 |
| `embedding` | 问题做一次云端 embedding，与内存中的实体向量矩阵算余弦相似度，取超过阈值的前 k 个 | 能处理换说法；多一次 API 调用；阈值需标定 |

### 7.2 输出
`{entities: [...], strategy: "dictionary" | "embedding" | "none"}`，写入轨迹。`none` 时跳过图谱定位证据。

### 7.3 代码落点
新建 `rag/entity_linking.py`；实体向量矩阵在启动或重建图谱后加载。

## 8. 图谱定位证据

### 8.1 遍历规则
| 规则 | 取值 |
|---|---|
| 方向 | 无向遍历；展示证据路径时保留原方向 |
| 最大跳数 | `max_hops`（默认 2） |
| 枢纽实体 | 可以作为路径终点，但不能作为中间节点继续扩展 |
| 起点是枢纽实体 | 只扩展 `start_hub_max_hops`（默认 1）跳 |
| 候选上限 | 出处 chunk 去重后最多 `max_candidates`（默认 30） |
| 可用关系 | 只使用 `chunk_ids` 非空的关系 |

### 8.2 查询示意
```cypher
MATCH p = (s:Entity)-[rs:REL*1..2]-(t:Entity)
WHERE s.name IN $starts
  AND all(r IN rs WHERE size(coalesce(r.chunk_ids, [])) > 0)
  AND all(n IN nodes(p)[1..-1] WHERE coalesce(n.degree, 0) <= $hub_degree)
RETURN [n IN nodes(p) | n.name] AS chain,
       [r IN rs | {type: r.type, chunk_ids: r.chunk_ids,
                   from: startNode(r).name, to: endNode(r).name}] AS rels
ORDER BY length(p) ASC
LIMIT 200
```
（原 `neo4j_client.get_paths` 为有向、子串匹配起点、无枢纽控制，不再用于问答。`*1..2` 为示意，实际跳数由 `max_hops` 拼入查询并做整数校验，与原 `get_paths` 防注入写法一致；起点为枢纽实体时单独用 `*1..1` 查询。）

### 8.3 从路径到证据
```
路径集合 → 收集各关系的 chunk_ids（去重，保留"该 chunk 来自哪条路径"）
 → 截断到 max_candidates（先按被几个不同的链接实体共同指向降序，再按路径长度升序、出现次数降序）
 → 从 MySQL Chunk 取正文，组装成与检索结果相同的条目结构（§16.1，small-to-big 规则与原检索一致）
 → 与原上下文合并去重 → 打分器统一 rerank → 取 topk
 → 进入再分级
```
- 最终进入上下文的 chunk 若来自图谱，记录其**证据路径**（如 `A -[属于]- B -[导致]- C`），供前端高亮和答案溯源。

- 候选排序多加的第一级（M6b 实测后调整）：问题常链接到"北京""董事长"这类泛化实体，它们一跳就连出几百条边；只按跳数排序时，这些边会占满候选名额。被多个问题实体共同指向的 chunk 更可能是答案所在。
- 路径查询按起点逐个执行、各自限额，避免邻居多的实体独占结果。

### 8.4 代码落点
新建 `rag/graph_evidence.py`；`clients/neo4j_client.py` 新增 `find_evidence_paths`。

## 9. 生成、拒答与证据补全
- 生成沿用 grid-qa 的引用式生成与引用校验。
- 拒答：纠错用尽仍为 incorrect 时，不生成答案，返回领域包配置的拒答措辞（M6c 已实现：`qa_service._refused_response`，非流式与流式一致，不调用 LLM）。原实现只在 prompt 里提示"优先回答无法确认"，模型仍会从无关资料拼出答案（qwen 下 tu01 即如此）。
- 拒答或低置信问题进入证据补全队列（沿用 `evidence_gap_service` + `knowledge_backbone`）。
- 演示闭环（P1）：拒答 → 证据补全草稿 → 人工确认 → 回流入库并补抽三元组 → 再次提问答对。

## 11. 评测框架（ADR 0007）

### 11.1 数据集构建
```
CRUD-RAG 原始数据（格式已于 09-27 核实）
 → 按事件抽样：单/双/三文档可答题各 30 + 不可答题 15（双 8、三 7），105 个事件互不相关
 → 语料 = 可答题的标准文档 + 与所有抽样事件无关的干扰新闻，共约 1000 篇
 → 不可答题：删除其全部标准文档
 → 划分标定子集（1/3，用于阈值标定）与测试子集
 → 输出 data/gcrag_eval/general/{questions.jsonl, corpus/, removed_docs.json, build_report.json}
```
构造规则与实测数据见 §16.13。事件互不相关，所以删除某题的文档不会误伤其他题。

### 11.2 运行
- 评测脚本对每道题分别以 `none / legacy / gcrag / 闭卷` 调用 `/qa/answer`，保存答案、分级、轨迹。
- 打分器使用录制回放。

### 11.3 判定
- LLM 对照标准答案判定"正确 / 错误 / 拒答"。判定模型为 Claude（与生成同一模型，ADR 0006 修订）；系统拒答（`cragAction=refused`）按规则直接判 refused，不经判定模型。
- 人工抽查 20%，报告判定一致率。

### 11.4 指标定义
| 指标 | 定义 |
|---|---|
| 准确率 | 按题型（单/双/三文档）统计判定为正确的比例 |
| 挽回率（动作 X） | 分母：初次分级为 ambiguous/incorrect 且执行了动作 X 的可答题；分子：其中在动作 X 之后分级变为可作答且最终答对的题 |
| 不可答题拒答率 | 不可答题中系统拒答的比例 |
| 可答题误拒率 | 可答题中系统拒答的比例 |
| 代价 | 平均纠错轮次、端到端延迟 P50/P95、LLM/embedding/rerank 调用次数 |
| 闭卷准确率 | 闭卷基线的准确率 |

### 11.5 阈值标定
在标定子集上扫描 `(high, low)` 网格，目标是在可答题误拒率不超过设定上限的前提下最大化准确率；报告扫描结果与最终取值。

### 11.6 附加实验（P1）：分级信号缺陷
在 legacy 模式下注入 rerank 故障（超时 / 无 key），对比修复前后的拒答率与"错误判为 correct"的比例。

### 16.2 打分器

```python
@dataclass
class ScoreResult:
    ok: bool
    scores: list[float]   # ok 时与 texts 等长、同序；失败时为空列表
    reason: str           # ok | timeout | error | no_key

class Scorer(Protocol):
    name: str
    async def score(self, query: str, texts: list[str], *, timeout: float) -> ScoreResult: ...

def get_scorer() -> Scorer    # 按 SCORER 选择实现，并按 SCORER_CACHE 包一层录制回放
```

- `DashscopeRerankScorer`：调用 gte-rerank-v2，`top_n = len(texts)`，把返回的 `(index, score)` 还原成输入顺序。**无 key 时返回 `ok=False, reason=no_key`**，不再像原 `rerank_service.py:44` 那样返回全 0 分。
- `CachedScorer(inner, mode, path)`：
  - 键 `sha256(f"{cache_id}|{query}|{text}")`，逐条缓存；`cache_id` 为"打分器@模型"（如 `dashscope_rerank@gte-rerank-v2`），换 rerank 模型不会回放旧分数；
  - `record`：全部未命中的文本合并成一次调用，结果写入 JSONL；
  - `replay`：命中的直接用，未命中的走 `record` 逻辑补录；
  - 任一条打分失败，整次返回 `ok=False`，不写入缓存。
- 检索中的 rerank 步骤（`retrieval_service.py:446-466`）改为调用 `get_scorer().score(...)`；原 `rerank_service` 只作为 `DashscopeRerankScorer` 的 HTTP 实现保留。

```cypher
MERGE (a:Entity {name: $s}) ON CREATE SET a.type = $s_type
MERGE (b:Entity {name: $o}) ON CREATE SET b.type = $o_type
MERGE (a)-[r:REL {type: $r}]->(b)
  ON CREATE SET r.doc_id = $doc_id, r.doc_name = $doc_name,
                r.doc_ids = [$doc_id],
                r.chunk_ids = CASE WHEN $chunk_id = '' THEN [] ELSE [$chunk_id] END
  ON MATCH SET  r.doc_ids = CASE WHEN $doc_id IN r.doc_ids THEN r.doc_ids ELSE r.doc_ids + $doc_id END,
                r.chunk_ids = CASE WHEN $chunk_id = '' OR $chunk_id IN coalesce(r.chunk_ids, [])
                                   THEN coalesce(r.chunk_ids, []) ELSE coalesce(r.chunk_ids, []) + $chunk_id END
```

- 保留 `doc_id` / `doc_name`（首个来源）以兼容现有读取代码。
- 建图完成后刷新度数：`MATCH (n:Entity) SET n.degree = COUNT { (n)--() }`。
- 实体 `type` 改由领域包 schema 给出，替换 `_infer_type` 的 Equipment/Fault/Action 推断（`neo4j_client.py:17-30`）。
- 已实现（M5b）：写入用 `UNWIND` 每 500 条一批；已有节点类型为空时才用新类型补上。度数在每次写入/删除后**只刷新受影响端点**（新增或删除一条边只改变两端的度数），全图刷新 `refresh_degree(None)` 留给重建脚本。`_infer_type` 只保留为读取旧节点（无类型）时的显示兜底。
- **按文档删除**（`delete_by_doc(doc_id, chunk_ids)`）：从边的 `doc_ids`/`chunk_ids` 中移除该文档及其 chunk，`doc_ids` 清空才删边，`doc_id` 若等于被删文档则改为剩余首个来源；删除后孤立的实体节点一并删除。原版按 `r.doc_id` 整边删除会误删其他文档支撑的边（§17）。没有列表的旧边按 `[doc_id]` 处理，被写入时自动升级。

**LLM 抽取输出**（扩展 `_parse_triples_v2`）：每条 `{"s", "r", "o", "s_type", "o_type", "chunk_no"}`，`chunk_no` 为批内 1 起编号。

**重建**：`scripts/rebuild_kg.py`：清空 `kg_triples`、Neo4j 全部 `:Entity` 与 `:REL`、`entity_embedding` → 逐文档抽取（记录已完成的 `doc_id`，支持断点续跑）→ 刷新度数 → 实体向量化 → 通知 `EntityIndex.reload()`（后端重启亦可）。

### 16.12 降级矩阵

| 故障 | G-CRAG 行为 | 对外表现 |
|---|---|---|
| 打分器失败（超时/无 key/错误） | 分级为 `unscored`，不纠错，直接生成 | `scoringOk=false`，`confidence=medium` |
| 实体向量召回失败 | 只用词典结果；词典也无结果则跳过图谱定位证据 | `linking.degraded="embedding_failed"` |
| 未链接到实体 | 跳过图谱定位证据，进入 LLM 改写 | round.status=`skipped_no_entity` |
| 图谱无路径 | 同上 | round.status=`skipped_no_path` |
| Neo4j 不可用 / chunk 读取失败 | 同上 | round.status=`unavailable` |
| 合并后重打分失败 | 丢弃图谱候选，保持原分级，进入 LLM 改写 | round.status=`failed` |
| LLM 改写失败 | 视为本轮未改善；仍为 incorrect 则拒答 | round.status=`failed` |
| 纠错用尽仍为 incorrect | 拒答，进入证据补全 | `cragAction=refused` |

所有降级同时调用 `degraded(tag, exc)`（日志 + Prometheus 计数，`core/obs.py:18-32`）。评测时，带降级的记录单独计数，不与正常记录混算。

产物目录为 `data/gcrag_eval/general/`（不入库，ADR 0007；后端容器挂载为 `/app/gcrag_eval`），不放在 `domain_packs/general/eval/`。

**构造规则**（依据 09-27 对 CRUD-RAG 的格式核查，数据放 `data/crud_rag/`，不入库）：
1. 题源用完整集 `CRUD_Data/{1doc,2docs,3docs}_QA.json`（各 3199 题），不用论文的 800 题 split（其中 25 道单文档题被改写过）。三个集合共享同一批事件 `id`，每个事件各出一题。
2. **按事件抽样**：可答题 90（单/双/三各 30）+ 不可答题 15（双 8、三 7）共 105 题，来自 105 个互不相同的事件，避免同一事件的不同题型互相提供答案。双/三文档题只选各片段出自不同原文的题（子串映射到 `80000_docs` 行号校验）。入选时再做**事件去重**：与已入选事件字面相关（见第 4 步）或语义相似度 ≥ 0.65（云端 embedding，事件描述 + 问题）即跳过。实测阈值 0.8 时"杜苏芮"台风洪涝一个大事件下仍入选了 6 个事件、大运会开幕入选 2 个（其中之一是不可答题），0.65 时两两最高降到 0.65 以下；0.65~0.70 之间两类都有（同一大事件的子事件 / 仅话题相近），取 0.65 宁严勿松。
3. **标准文档 = 题目内联的 `news*` 片段原文**，`docId = sha1(text)[:12]`，按文本去重。不回查官方语料：单文档题的来源约 99% 不在语料中，双/三文档题的片段约 43% 跨越相邻的无关文章。
4. **干扰文档**：从 `80000_docs` 的 45 个 `documents_dup_*` 文件选取（排除 `documents_hallu*`，那是另一任务的旧闻），先按长度（200~2000 字）、近重复（去空白标点后前 200 字）、繁体重复过滤，再用两道关剔除与任一抽样事件相关的报道：
   - **字面**：命中该事件描述中的专名（书名号/引号内），或命中其 ≥ 2 个稀有 4 字片段；专名与片段都要求语料行频 ≤ 30。只取事件描述、不取标准文档里的引号内容——实测后者多为"人民日报""一带一路"之类泛化词，会误剔大量无关新闻。
   - **语义**：正文前 500 字与任一事件（描述 + 问题）余弦相似度 ≥ 0.65。实测只用字面规则时，保留下来的干扰文档中相似度 ≥ 0.7 的 18 篇几乎都是抽样事件的其他报道（齐齐哈尔体育馆坍塌、特朗普被起诉、京津冀暴雨等）。
   最后随机取足，使语料总数为 1000 篇。两道关的抽查样本写入 `related_samples.jsonl`。
5. **不可答题**：15 题（双 8、三 7）**删除其全部标准文档**（记入 `removedDocIds` 与 `removed_docs.json`），`answerable=false`，正确行为是拒答。原设计"只删一篇"不成立：多文档题的几篇片段常是同一事件的不同报道，实测被删片段与同题剩余片段的余弦相似度多在 0.74~0.97（如双色球同一期开奖的两篇报道），答案仍在语料中。改为全删后，被删文档与剩余语料的最高相似度为 0.764（双色球对大乐透，不同彩种与期号，不含答案），其余 ≤ 0.71。
6. `split`：可答题每个题型、不可答题各取 1/3 作标定集（阈值标定只用它），其余为测试集。
7. 实测（seed=20260927）：语料 1000 篇 = 标准文档 180 + 干扰文档 820；字面剔除 60、语义剔除 86、事件同簇跳过 14；构建耗时约 80 秒（含两次 embedding，费用可忽略）。

`scripts/gcrag_eval.py` 子命令：`build`（抽样、构造不可答题、导入语料）、`run --modes none,legacy,gcrag,closed_book`、`judge`、`report`（生成指标表与图）。闭卷基线不走 `/qa/answer`，直接调用 LLM。

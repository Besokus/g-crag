| 判定 | 条数 |
|---|---|
| 出处 chunk 正确 | **50 / 50（100%）**，验收标准 ≥ 90% |
| 三元组本身有质量问题（与出处无关） | 11 / 50：关系方向反了 3 条（"活动 举办 主办单位""火箭 研发 公司""部门 任职于 人名"）；关系用错 4 条（"特朗普 提出 敲诈勒索"实为被指控、"公安处 举办 侦查工作"等）；无信息量 3 条（"上海 影响 行业创新"等）；取了旧值 1 条（通行时间取了"缩短前的 60 分钟"） |
| 实体名只剩半边引号或书名号 | 4 / 50（"魔兽》电影""外贸“新三样"等） |

**发现与处理**：
1. **引号剥离规则有缺陷，已修复。** 通用包原规则把首尾引号分开剥，`《魔兽》电影` 会被剥成 `魔兽》电影`。全库统计有 178 个实体（1.9%）、341 条三元组（3.8%）名字里引号不成对。现在只剥"成对且包住整个名字"的引号；还有一部分是 LLM 输出本身就漏了半边，规则修不了。修复后需要重建才能生效。
2. **内容审核拒绝是确定性失败。** 1 篇新闻的一个批次被百炼内容审核拒绝，按原逻辑算作"失败、待重试"，重建会一直停在 PARTIAL。现在这类批次单独计为 `rejectedBatches`：文档算完成，但数量会在汇总里列出。
3. **图谱稀疏。** 新闻语料的事件之间彼此独立，72% 的实体只有一条边。M6 的图谱证据应以"一跳 + 出处 chunk"为主，多跳路径预计很少；这个结论要写进报告里的消融分析。

## M6 多跳演示集尝试（2026-10-02，结论：本语料上构造不出"检索漏召、图谱挽回"的样例）

验收标准原定为"构造的多跳样例中原有纠错失败、G-CRAG 挽回"（开发方案 M6）。构造方法（`scripts/gcrag_multihop.py`）：从图谱取跨文档 2 跳路径 A -[r1]- B -[r2]- C（r1、r2 出自不同文档，A、C 不直接相连，B 非枢纽，端点名不包含 B），固定种子每个桥接实体 / 每篇文档至多用一次，抽 30 条；Claude 按路径两端的出处 chunk 出题，题目只提 A、不得出现 B、C 及文档 2 中的其他专有名称，答案取自文档 2；再对每题做检索探测（与问答同路径、强制打分，top5）和图谱探测。

| 结果 | 题数 |
|---|---|
| 出题无效（生成器放弃 / 题目泄露 B 或 C） | 9 |
| 起点实体 A 未被链接 | 2 |
| 有效且 A 被链接 | 19 |
| 其中检索 top5 召回文档 2 | **19**（排名 1：10 题，2：8 题，4：1 题） |
| 其中图谱定位证据可到达文档 2（不排除已召回 chunk） | **19** |

- **真实挽回 1 道（t12）**：初始 ambiguous，gcrag 的图谱轮次采纳 0 条、答错；两个路径模式用"问题 + 路径三元组"重打分后采纳 1 条图谱出处 chunk（top1 0.253 → 0.346），答对。这是全部评测中第一道"图谱证据进入上下文且答案由错变对"的题。
- **gcrag_path 比 gcrag 少的 3 道里，d30、t22 与图谱无关**：两种模式在这两题上都是 normal、没有纠错轮次、检索来源完全相同，判定不同纯属生成随机性。上下文完全相同的 53 题中，判定翻转 2 道（3.8%），与 test3 的观察一致。

**结论**：

2. 关闭三元组注入后 none 从 86.7% 降到 83.3%（d19、t12 由对变错，s26 由错变拒答），方向上说明三元组注入有用，但 2 题差异同样在随机性范围内。
3. 本语料上大部分题首轮即被判为 correct（53/70），纠错模式只作用于剩余 17 题，这是"有条件有效"的主要原因。

## 隐藏桥接子集 hard1（2026-10-03，31 题，结论：图谱定位证据在"语义不可达的多跳"上有效）

**构造**（`scripts/gcrag_multihop.py hard`，方法参照 MuSiQue 的去捷径思路，见 `docs/g-crag/research/2026-10-02-graphrag-multihop-routing.md`）：从图谱 3274 条跨文档 2 跳路径 A -[r1]- B -[r2]- C 中，按"文档 2 不含 A、文档 1 不含 C、B 在 r2 关系上的邻居 ≤ 3"筛出 345 条（每个 B 至多 3 条，固定种子）。Claude 看两篇出处 chunk 出题，题目只能用文档 1 的信息指代 B，答案取自文档 2；再依次过滤：

**评测**（提交 `6cead3e`，阈值 0.30 / 0.18，Claude 生成与判定，并发 1、间隔 6s，0 次 403；完整表见 `docs/g-crag/eval/hard1_report.md`）：

## 证据补全闭环在线演练（2026-10-07，演示第 4 步）

演练题："2026年上海理工大学计算机综合创新开发课程的项目演示安排在哪一天？"（语料中没有，适合演示"拒答 → 补全 → 可答"）。

**演练中发现的缺陷**：AI 续写在资料不足时给出的草稿结论是"根据现有资料无法确认"，状态变为"已续写"后管理页直接显示「✓ 确认同步」，确认接口在未人工编辑时用 AI 草稿兜底——这条非答案被当成 FAQ 入库，并以 high 置信写进所有纠错模式的缓存，之后再问就命中缓存、以高置信返回"无法确认"。修复：`confirm_and_sync` 在最终答案第一段（结论）为"无法确认 / 无法回答"一类时拒绝同步，提示先人工编辑（单测 5 项）。误发布的 FAQ 文档已删除，关联缓存随文档删除失效，重新提问恢复为结构化拒答。

**修复后的完整流程**（问答页默认模式 gcrag）：

| 步骤 | 结果 |
|---|---|
| 1. 提问 | 结构化拒答（refused，分级 incorrect），自动收集为证据缺口，来源 CRAG |
| 2. AI 续写 | 草稿结论"现有资料无法确认"（检索放宽到 top10，未编造） |
| 3. 不编辑直接确认同步 | **被拒**："答案结论为'无法确认'，不能作为知识入库，请先人工编辑最终答案" |
| 4. 人工编辑最终答案 → 确认同步 | 入库为 FAQ 文档（1 个 chunk），向量化，逐纠错模式写缓存 |
| 5. 原问题再问 | high，命中 Redis 缓存，来源为该 FAQ |
| 6. 换个问法、跳过缓存再问 | high，分级 correct，检索 top1 即该 FAQ（rerank 0.948），答出 2026年10月9日 |
| 7. 图谱 | 后台自动抽取 2 条三元组（上海理工大学 —举办→ 计算机综合创新开发课程 —发生于→ 2026年10月9日），出处校验 verified，Neo4j 边带出处 chunk |

**演示前复位**：在知识库页删除该 FAQ 文档（联动删向量、三元组、Neo4j 边并失效缓存），在系统管理 → 证据补全删除该缺口，即可在现场重走一遍。

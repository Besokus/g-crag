# 基于项目现状的新方向调研报告

> **版本:** v1.0 | **日期:** 2026-08 | **依据:** 全量代码审计（`config.py` 全部开关 / `services/`+`rag/` 模块清单 / git log 近 40 提交 / `docs/` 规划）+ 行业桌面调研（学术 + 产业 + 电网央企实践）
> **定位:** 回答"这个项目下一步该往哪走"，每条建议给出本仓库的具体落地点，可直接转成 sprint 任务。

---

## 一、调研结论速览

本项目在"**知识检索问答**"这条纵轴上已经做得非常深（混合检索 / CRAG / GraphRAG / 三级缓存 / 引用校验 / 评测闭环 / 数据飞轮 / Agent+MCP / 数字孪生 / 可观测性全部在列），**稀缺的不是"更多 RAG 技巧"，而是三件事**：

1. **从"问"到"办"的行动闭环** —— BRD 当年明确排除"实时监控接入"和"作业闭环管理"，这两个排除项恰恰是行业 2025-2026 最热的落点（检修计划一键生成、主动抢修）；
2. **真实数据/系统接入** —— 目前 SCADA 是 mock、CIM 是"设计完成实现延后"、无真实遥测，行业案例全部建立在真实数据上；
3. **已建成能力的灰度验证** —— 十几个 opt-in 开关（CRAG V3、引用五层校验、语义缓存、debate agent、路由感知调参等）建好了但还没逐个用评测数据证明价值。

**优先级建议：P0 做"行动闭环 + 真实数据 + 评测驱动"，P1 做"CIM 孪生 + 时序问答 + 多模态 + 语音移动端 + 主动运维"，P2 做"领域微调私有化 + 规模化 + 合规纵深 + 架构前沿跟随"。**

## 三、行业趋势扫描（2025-2026）

### 3.1 RAG 技术演进：从"检索技巧竞赛"转向"系统化工程"

- **GraphRAG / Agentic RAG 成为主流叙事**，但学界开始冷静评估："我们还需要 GraphRAG 吗？"——对 Agentic 检索系统做 benchmark，结论是 GraphRAG 在**多跳/关系型查询**上仍显著有效（[arxiv 2604.09666](https://HuggingFace.co/papers/2604.09666)、[arxiv 2606.25656](https://arxiv.org/abs/2606.25656v1)）。
- **长上下文 vs RAG 不是二选一**：LaRA benchmark 的结论是"没有银弹"，**LC/RAG 混合路由**（简单问题直接长上下文，复杂问题走检索）才是正解（[LaRA @ ICML 2025](https://mlanthology.org/icml/2025/li2025icml-lara/)）。
- **LightRAG 等简化图 RAG** 降低 GraphRAG 落地成本（[LightRAG (EMNLP 2025)](https://github.com/deepshukla/LightRAG)）；"2025 年的 RAG 课程 2026 年就过时"的说法印证范式仍在快速迁移（[腾讯云开发者](https://cloud.tencent.cn/developer/article/2649980)）。

### 3.2 电力行业大模型格局：央企自建大模型已成事实标准

- **国网"光明"大模型、南网"大瓦特"、AI EPS** 三大电力 AI 系统是行业参照系，覆盖设备运维、调度、客服等场景（[怀柔实验室对比](https://www.sgpjbg.com/labelsyh/zhinengdianwangdamoxing.html)）。
- **工信部发布 285 项 AI 典型案例，国家电网、南网、各大能源央企全部入选**——"AI+电力"是政策明确鼓励方向（[名单报道](https://www.163.com/dy/article/L21J3CI70552F81B.html)）。
- 省级电网实践：安徽电网"光明"解法（[北极星](https://news.bjx.com.cn/html/20250422/1438002.shtml)）、上海电网"AI 大脑"上线（[上海市政府](https://www.shanghai.gov.cn/nw4411/20250409/8b9b9063fba942049277ea58f62d27d8.html)）。

### 3.3 智能体运维：从"知识问答"走向"诊断-决策-执行"

- **DiagAgent（IEEE 2025）**：RAG + MCP 工具集成的电力设备故障诊断 Agent 框架——与本项目 `agent_runtime + mcp + kg_service + retrieval` 架构几乎同构，**证实本项目的 Agent 方向走在行业前沿**（[IEEE](https://ieeexplore.ieee.org/abstract/document/11413511)）。
- **SmartGridBench**：基于 IBM AssetOpsBench 的智能电网变压器维护 benchmark，用 MCP/direct-call 双工具面评测 tool-using LLM agent——**本项目缺一个同类评测面**（[GitHub](https://github.com/eggrollofchaos/hpml-assetopsbench-smart-grid-mcp)）。
- **PowerSkills**：电力系统分析 agent skills（仿真/潮流/优化）开源集合，可作为 MCP 工具扩展参照（[GitHub](https://github.com/Power-Agent/PowerSkills)）。
- 产业落地：国网青海"检修计划一键生成"（[科技日报](https://www.stdaily.com/web/gdxw/2025-06/20/content_358100.html)）、"闽捷 AI 主动抢修指挥官"从被动抢修走向主动感知（[东方财富](https://caifuhao.eastmoney.com/news/20260509210435403747820)）。

### 3.4 可信与治理：幻觉缓解从"启发式"走向"证据化"

- **HalluGuard**：基于证据的小型推理模型专门缓解 RAG 幻觉，可作本地裁决器（[HuggingFace paper 2510.00880](https://huggingface.ac.cn/papers/2510.00880)）。
- **可信 Agent 统一评测治理框架**成为研究热点（[TechRxiv](https://www.techrxiv.org/doi/full/10.36227/techrxiv.176799772.28164151/v1)）；幻觉工程指南强调"引用 + 验证 + 兜底 + 评测"四件套（[Jimmy Song 可靠性手册](https://jimmysong.io/zh/book/ai-handbook/playbook/hallucination/)）。

## 四、差距分析（现状 vs 行业）

| 行业趋势 | 本项目现状 | 差距 / 机会 |
|---|---|---|
| 检修计划/工单一键生成 | 有 `ticket_lifecycle` + `ticket_audit` + agent 工具，但**没有"问答→工单自动起草→流转"闭环** | 行动闭环缺失是最大空白 |

| 多模态 | `VLM_ENABLE=False` 默认关，`multimodal_service` 存在 | 图纸/红外/表计场景未开闸 |

| 安全合规纵深 | RBAC/ACL/审计齐备，**PII 脱敏默认关、无红队评测、无等保密评准备** | 强监管行业上线前必须补齐 |

## 五、新方向建议（按优先级，附本仓库落地点）

### P0 —— 1~2 个迭代（4~6 周），收益最快

#### 方向 1：问答→行动闭环：Agent 化工单工作流（"问"到"办"）
- **内容**：在现有问答/Agent 之上加"诊断 → 自动起草工单 → 人工审批 → 派发 → 处置回填"闭环。用户问"1 号主变油温高怎么办"→ Agent 检索+图谱+遥测 → 产出处置方案 → 一键生成工单（含步骤、风险、引用依据）→ 值班长审批 → 派发 → 处置完成后回填知识库（喂给知识自进化）。
- **行业依据**：检修计划"一键生成"已成央企标配（[科技日报](https://www.stdaily.com/web/gdxw/2025-06/20/content_358100.html)）；BRD 当年的"排除范围"（作业闭环管理）现在正是补位点。
- **落地点**：`ticket_lifecycle_service.py`（补 draft/approve/dispatch 状态机）· `agent_tools.py` 新增 `draft_ticket`/`review_ticket` 工具 · `agent_personas.py` 新增 `ops_planner` persona · 前端工单页 + 审批视图 · `quality_event_bus` 派发状态事件。

#### 方向 2：真实数据接入：SCADA / MIS 实时数据 MCP（"活数据"问答）
- **内容**：把 `mock_scada` 替换/并存为真实数据适配器（IEC 104 / Modbus / OPC-UA / 或电网 REST 网关），让 Agent 能答"1 号主变当前油温/负荷/告警"。告警经 `realtime_event_service` 落库并触发主动推送。
- **行业依据**：DiagAgent 的 RAG+MCP 架构已验证"静态知识 + 实时遥测"混合诊断是刚需（[IEEE](https://ieeexplore.ieee.org/abstract/document/11413511)）。
- **落地点**：`mcp/` 新增 `scada_gateway.py`（协议适配层，mock 保留为回退）· `MCP_SERVERS` 配置 · `realtime_event_service.py` 告警→Agent 触发 · 前端遥测卡片。

#### 方向 3：已建能力灰度验证 + 评测对照（"把武器上膛"）
- **内容**：对 11 个默认关的 opt-in 能力（`CRAG_V3_ENABLE` / `CITATION_VERIFIER_ENABLE`+NLI / `SEMANTIC_CACHE_ENABLE` / `DEBATE_ON_LOW_CONFIDENCE_ENABLE` / `SUFFICIENCY_GATE_ENABLE` / `RRF_ROUTE_AWARE_ENABLE` / `MULTI_TURN_CACHE_ENABLE` / `HYDE/MULTI_QUERY/SELF_RAG/RAPTOR`）逐个做"开/关"评测对照（复用 golden + LLM-judge + retrieval eval），按数据决定常开或回收。产出"能力收益矩阵"文档。
- **行业依据**：2025-2026 RAG 工程共识——**任何高级能力必须用评测证明收益**，否则只是复杂度（[LaRA 混合路由结论](https://mlanthology.org/icml/2025/li2025icml-lara/)、[幻觉工程指南](https://jimmysong.io/zh/book/ai-handbook/playbook/hallucination/)）。
- **落地点**：`scripts/eval_suite.py` 扩展"开关对照模式" · `online_eval_service` 按开关维度聚合 · 新增 `docs/能力收益矩阵.md` · `retrieval_tune_service` 复用。

#### 方向 4：电力 QA 评测基准 + 红队对抗评测
- **内容**：建设 500~1000 条电网 golden 集（变/配/输三场景，含多跳、指代、过时知识、拒绝类）→ 接入 `validate_golden.py` 格式门禁；新增红队用例集（prompt injection、诱导幻觉、越权探测、过时文档诱导），上线前必跑。可对标 SmartGridBench 的 MCP 工具评测面（[GitHub](https://github.com/eggrollofchaos/hpml-assetopsbench-smart-grid-mcp)）。
- **行业依据**：可信 Agent 需要统一评测与治理框架（[TechRxiv](https://www.techrxiv.org/doi/full/10.36227/techrxiv.176799772.28164151/v1)）。
- **落地点**：`tests/golden/` 扩展 · 新增 `tests/redteam/` · `scripts/eval_suite.py` 增加红队报告 · CI 加入红队冒烟（轻量）。

### P1 —— 中期（2~3 个月），构建行业纵深

#### 方向 5：CIM 拓扑数字孪生落地（标准拓扑 + 真实连通）
- **内容**：拿到真实 CIM/CIMD 后启动：`cim_parser` 全量解析 → 拓扑处理（开关态合并→带电岛）→ `twin_service` 读图替代 JSON 布局 → 故障传播链按真实连通+开关态 BFS → 与 GraphRAG 打通（CIM 连通图作结构层）。
- **依据**：项目自己的设计稿已论证并给出最小切片路径（[docs/sprint3a-cim-topology-design.md](../docs/sprint3a-cim-topology-design.md)）；CIM 数字孪生是行业标准化基线。
- **落地点**：`cim_service.py` / `cim_parser.py` · `twin_service._load_layout` 改造 · `kg_service` CIM 子图 label · 前端布局自适应。
- **前置依赖**：真实 CIM 数据（关键路径）。

#### 方向 6：时序数据问答（Time-series RAG）
- **内容**："过去 24h 油温趋势 / 负荷高峰出现在几点 / 该遥测异常持续多久"等数字+文本混合问答；检索（文本召回设备+指标）+ 数值查询（时间窗口聚合）+ 生成（自然语言结论 + 图表）。复用双 embedding 库存元数据，新增时序索引（Milvus 标量过滤或并入现有 collection）。
- **落地点**：新 `services/ts_qa_service.py` · 遥测入库 pipeline（接方向 2 的真实数据）· `multimodal_service` 图表生成 · 前端趋势图组件。

#### 方向 7：多模态开闸（VLM 图纸/红外/表计）
- **内容**：`VLM_ENABLE` 灰度上线：图纸问答（电气接线图定位）、红外热像异常识别、表计读数、缺陷照片检索；与 `rapidocr` 管线协同（OCR 得文本、VLM 得空间语义）。
- **落地点**：`multimodal_service.py` 补 prompt/链路 · `parse_service.py` 图像分支 · `VLM_ENABLE` 开关 + 评测对照（方向 3 机制复用）。

#### 方向 8：语音 + 移动端现场作业
- **内容**：语音提问/答案播报（ASR+TTS，注意容器内不可设代理的既有约束）、移动 H5 适配、弱网离线缓存；现场拍照→设备识别→定向检索（与方向 7 联动）。
- **行业依据**：现场作业是"10~15 分钟→10 秒"效率叙事的主战场，语音是刚需交互。
- **落地点**：前端新入口 `views/MobileQA.vue` · 后端语音网关 service · 现有 API 全兼容（响应已含 trace/引用）。

#### 方向 9：主动运维：告警→根因→处置预案→确认派发
- **内容**：把 `fault_prediction`（风险分）+ `alert_disposal`（告警处置）+ KG 传播链（`get_paths`）串成自动链路：告警入 `realtime_event_service` → Agent 自动检索+图谱推理出根因与处置预案 → 推送值班员确认 → 确认后一键派发工单（接方向 1）。"闽捷 AI 主动抢修指挥官"正是此模式（[案例](https://caifuhao.eastmoney.com/news/20260509210435403747820)）。
- **落地点**：`alert_disposal_service.py` 加预案生成 · `fault_prediction_service.py` 结果消费 · `agent_runtime` 后台诊断 persona · `realtime_event_service` 触发。

### P2 —— 长期/战略（3 个月+）

#### 方向 10：行业大模型微调 + 私有化推理（对标"光明/大瓦特"自建路线）
- **内容**：按既有规划（[100 万训练 + 30 万微调 对应模型及硬件参数.md](../100万训练数据+30万微调数据%20对应模型及硬件参数.md)）做 Qwen-7B 级 LoRA 领域微调 → vLLM 量化推理 → 作为 `providers/llm` 新 provider 接入（与云端 fallback 链并存，云断→本地不降级）；先小步验证"微调 7B vs 云 API"在 golden 集上的收益再决定投入。
- **落地点**：`providers/llm/vllm_provider.py` · 微调流水线脚本（`scripts/finetune/`）· 评测对比报告。
- **风险**：硬件/数据成本高，**必须先出对比数据再立项**。

#### 方向 11：多站点/知识联邦 + 私有化交付
- **内容**：跨变电站/地市局知识协同（知识共享 + 数据不出域）、单租户私有化交付模板、资源隔离；现有 tenant 体系是现成底座。
- **落地点**：tenant 模型扩展 · 部署模板（docker-compose 变体）· 文档。

#### 方向 12：安全合规纵深（强监管上线前置）
- **内容**：等保 2.0/密评准备、`PII_MASK_ENABLE` 开闸 + 效果评测、prompt injection 红队（接方向 4）、内容审核、全链路审计闭环（操作日志 + agent 工具审计已有底座）。
- **落地点**：`core/safety.py` 强化 · `agent_tool_audit_service.py` · `PII_MASK_ENABLE` · 红队用例。
- **依据**：电力是强监管行业，安全合规是硬约束（本项目 BRD/AGENTS 反复强调）。

#### 方向 13：RAG 架构前沿跟随（小步、可回退）
- **内容**：评估 Late Chunking（长文切块保语义）、LC/RAG 混合路由（简单问直接长上下文省延迟，复杂问走检索——呼应 LaRA 结论）、HalluGuard 式轻量证据裁决器（本地化幻觉拦截，替代部分重 NLI）。
- **落地点**：`chunk_service.py` 切块策略 · `routing_service.py` 路由档扩展 · `rag/judge.py` 本地裁决器。

## 六、路线图（建议排期）

| 阶段 | 周期 | 内容 | 关键产出 |
|---|---|---|---|
| P0 | 4~6 周 | 方向 1 工单闭环 · 方向 2 真实 SCADA MCP · 方向 3 能力灰度对照 · 方向 4 评测基准+红队 | 工单闭环可用；首个真实数据源；能力收益矩阵；红队报告 |
| P1 | 2~3 月 | 方向 5 CIM 孪生 · 方向 6 时序问答 · 方向 7 多模态 · 方向 8 语音移动端 · 方向 9 主动运维 | 标准拓扑孪生；遥测问答；VLM 灰度；移动端；告警自动预案 |
| P2 | 3 月+ | 方向 10~13 微调私有化 · 知识联邦 · 合规纵深 · 架构前沿 | 私有化推理；多站点交付；等保准备；架构演进评估 |

**依赖提醒**：方向 2 是方向 6/9 的前置；方向 5 依赖真实 CIM 数据；方向 10 必须先做评测对比再立项。

## 七、风险与约束

1. **真实数据获取是 P1 关键路径**：SCADA/CIM/遥测数据不落地，方向 5/6/9 只能停在 demo。
2. **云端 API 依赖**：深度使用场景受供应商稳定性/成本制约，私有化推理（方向 10）是长期解，但决策要数据驱动。
3. **能力复杂度蔓延**：十几个 opt-in 开关若不做方向 3 的评测对照，会变成"没人敢开的死代码"——评测先行是纪律。
4. **合规红线**：语音（隐私）、遥测（生产数据）、多租户共享（越权）都要过安全评审；PII 脱敏默认关的现状在真实上线前必须处理。
5. **容器代理/离线约束**：所有新增出站调用（ASR/TTS/VLM/微调）都要遵守"容器内不设 HTTPS_PROXY、HF 离线缓存"的既有约定。

## 八、结论

一句话：**纵轴已深、横轴待扩**。本项目的"知识问答纵深"已具备行业旗舰水准，下一个值得投入的新方向不是"再叠一层 RAG 技巧"，而是按 **P0（行动闭环 + 真实数据 + 评测驱动）→ P1（CIM 孪生 + 时序/多模态/语音 + 主动运维）→ P2（微调私有化 + 合规 + 规模化）** 的顺序，把系统从"会回答"升级为"会诊断、会起草、会闭环"，并让每个新能力都有评测数据背书——这正是 2025-2026 电网央企大模型应用（光明/大瓦特/检修一键生成/主动抢修）证明的路径。
